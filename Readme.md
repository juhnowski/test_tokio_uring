# Версия 0.1.0
# Описание алгоритма
Полностью исключены накладные расходы на переключение контекста ядра (через системные вызовы syscall) и Page Cache:
- io_uring (через tokio-uring) 
- O_DIRECT | O_SYNC 
- выравниванием памяти через posix_memalign

 Старые системные вызовы (вроде pwrite) заставляют процессор постоянно переключаться в режим ядра и обратно, а код через tokio-uring делает иначе:
- Он создает две очереди прямо в памяти:
  - __Submission Queue (SQ)__ - куда отправляете запрос методом .submit()
  - __Completion Queue (CQ)__ - откуда забираем результат через .await.
- Контроллеры дисков Samsung 970 EVO / EVO Plus аппаратно поддерживают многоочередность. io_uring «скармливает» драйверу NVMe данные напрямую, позволяя аппаратному обеспечению диска обрабатывать запросы параллельно, без пауз со стороны CPU.

# Обоснование констант
## DATA_SIZE = 512
В коде вы выделяете непрерывный буфер размером 512 МБ и записываете его одним огромным куском (write_at(write_buf, 0)). Для NVMe это называется последовательной (линейной) записью большого блока.

- Для Samsung 970 EVO Plus (nvme_final): 512 МБ — это крошечный объем. Скорость записи в 2082 МБ/с означает, что его SLC-кэш (Intelligent TurboWrite) без проблем «проглотил» весь этот объем за 0.24 секунды, даже не заметив нагрузки.

- Для старого Samsung 970 EVO (nvme_new): Несмотря на то, что буфер тоже помещается в кэш, базовая скорость записи самих кристаллов памяти (V-NAND 4-го поколения) ниже. Контроллеру Phoenix на старом диске приходится тратить больше циклов на кодирование сигнала при записи в ячейки, поэтому он выдал 1441 МБ/с.

# Сравнение
## SPDK - Поллинг
Полностью захватывает процессорные ядра. Он отключает обработку прерываний ядра Linux и гоняет бесконечный цикл (while true), опрашивая контроллер NVMe и сетевую карту напрямую через PMD-драйверы (через DPDK).
- Плюс: Нулевая задержка (минимальный latency).
- Минус: Потребление CPU всегда 100% на выделенных ядрах, даже если по сети не идет трафик. Сложно утилизировать эти же ядра под другие задачи.

## tokio-uring - Прерывания/Ринги
Использует общие очереди (Submission/Completion Queue) между вашим приложением и ядром Linux. Вы отправляете пачку запросов в ринг и засыпаете (или переключаетесь на другие задачи Rust-асинхронности), пока ядро (или его ядерный поток SQPOLL) занимается обработкой.
- Плюс: Эффективное использование CPU. Если нагрузки нет, процессор отдыхает. На одном ядре можно эффективно смешивать бизнес-логику, метрики и IO.
- Минус: Латентность (latency) может быть чуть выше, чем у честного поллинга SPDK, из-за накладных расходов на координацию с ядром (хотя режим IORING_SETUP_SQPOLL максимально приближает io_uring к производительности SPDK).

- 970 EVO Plus инженеры полностью переписали микропрограмму (прошивку) и оптимизировали алгоритм TurboWrite. Накопитель эффективнее сбрасывает данные из кэша в основные ячейки, за счет чего скорость прямой записи (даже мимо кэша) держится на уровне ~2300 МБ/с. На производительность чтения сильно влияет __фрагментация данных на физических кристаллах флеш-памяти__ и текущая температура чипа в момент обращения. Вероятно, структура ячеек на nvme0 в момент теста позволила контроллеру прочитать блоки данных более параллельно (задействовав больше каналов одновременно).

# Физическая фрагментация на NVMe живет своей жизнью
## 1. Слой абстракции: Секретная ОС внутри диска (FTL)
Когда отправляем команду записи в Linux на адрес /dev/nvme0n1p1, диск получает лишь логический адрес сектора (LBA).Внутри каждого накопителя Samsung 970 установлен мощный собственный процессор (контроллер ARM), на котором крутится __своя изолированная операционная система__. Главная её часть называется FTL (Flash Translation Layer — слой трансляции флеш-памяти
## 2. Алгоритм Wear Leveling (Выравнивание износа)
Флеш-память изнашивается от перезаписи. Чтобы диск не умер за пару месяцев, контроллер NVMe использует алгоритм __Wear Leveling__:Он намеренно разбрасывает (фрагментирует) записываемые файлы по самым «свежим» и наименее изношенным ячейкам.
Поскольку история «пробега» у дисков разная, контроллеры физически не могут разложить файлы в одинаковом порядке.

## 3. Разный размер физических блоковНа логическом уровне (в Linux): 
вы работаете с блоками по 4 КБ или файловой системой ext4, где все секторы кажутся одинаковыми.На физическом уровне (в кристаллах Samsung): память стянута в огромные блоки (Pages и Blocks) размером по несколько мегабайт. Причем у 64-слойной памяти (nvme0) и 92-слойной (nvme1) физическая геометрия этих блоков отличается на уровне полупроводников. Контроллер физически вынужден упаковывать данные в них по разным схемам.
